# 图片格式转换系统 待修复问题清单

> 适用范围:`Pancake\Server\FastAPI` 后端的图片格式转换系统。
> 涉及文件:
> - `app/controllers/PictureSwitchController.py`
> - `app/services/PictureSwitch/PictureSwitchService.py`
> - `app/services/PictureSwitch/PictureSwitchImageIO.py`
> - `app/services/PictureSwitch/PictureSwitchPILService.py`
> - `app/services/PictureSwitch/PictureSwitchSvgService.py`

> - `app/utils/PictureSwitchUtils.py`

> 说明:本文档所有问题均来自代码层面的静态分析,未经过实际运行验证;标注了"依赖依赖库行为"的条目需要在对应版本下实测确认。

## 一、功能性错误(代码内部自相矛盾或必然触发)

### 1. `quality=0` 被 Form 校验拒绝,与 WebP/AVIF 的 0–100 范围矛盾

- **位置**:`PictureSwitchController.py` 的 `convert_picture`
- **现状**:
  - Controller 声明 `quality: Optional[int] = Form(None, ge=1, le=100)`(下限 1);
  - `PictureSwitchUtils.FORMAT_DETAILS` 中 `webp`、`avif` 的 `quality_range=(0, 100)`,前端滑块 min 为 0;
  - `get_save_kwargs` 内明确支持 0:"WebP 接受 quality=0(极端压缩)"、"AVIF 接受 quality=0",并做了 `max(0, min(100, quality))` 钳位。
- **后果**:用户将 WebP/AVIF 质量拖到 0 提交时,整个请求被 FastAPI 422 拒绝(而非仅该文件失败);后端为 0 准备的钳位逻辑永远执行不到。
- **修复方向**:`quality` 的 Form 下限按目标格式区分(WebP/AVIF 允许 0),或在 Form 层放宽到 `ge=0` 后在服务层按格式钳位。

### 2. PBM/PGM 作为输出格式必然失败:`format="PBM"/"PGM"` 不是 Pillow 注册的格式名

- **位置**:`PictureSwitchUtils.EXT_TO_FORMAT`(`.pbm → "PBM"`、`.pgm → "PGM"`),`_convert_one_sync` 最终执行 `img.save(buf, format="PBM"/"PGM")`
- **现状**:Pillow 的 PPM 插件只注册格式名 `PPM`,`.pbm/.pgm/.ppm` 都只是它的扩展名别名,`SAVE` 注册表中不存在独立的 `PBM`/`PGM` 键。
- **后果**:`img.save(format="PBM")` 抛 `KeyError: 'PBM'`(同样 `'PGM'`),被 `convert_stream` 的通用 `except Exception` 吞掉,用户只看到"转换失败: 'PBM'"。目标格式为 pbm/pgm 的转换实际上从未成功过。
- **补充隐患**:即使把格式名改为 `PPM` 跑通,PPM 插件的 `_save` 按图像 mode 写文件头(RGB→P6、L→P5),而 `resolve_color_mode` 的 auto 分支对 PBM 只落在 `no_alpha_formats` 处理(返回 RGB),不会产出 PBM 要求的 1 位 `"1"` 模式——输出的 `.pbm` 文件内容会是 PPM 数据,文件与扩展名不符。
- **修复方向**:统一使用 Pillow 注册的格式名保存;若保留 PBM/PGM 输出,需在保存前强制转换到对应模式(PBM→"1"、PGM→"L")并验证写出内容与扩展名一致。

### 3. EXIF Orientation 未应用,照片方向会错

- **位置**:`PictureSwitchService._convert_one_sync` 全程没有 `ImageOps.exif_transpose` 之类调用;且 `strip_metadata` 默认 `True`,`img.info.clear()` 会连同 EXIF Orientation 一起清掉。
- **后果**:手机/相机竖拍照片(EXIF Orientation=6 等)在原图查看器中显示正常,转换后像素不旋转、方向标记又被删除,输出图片"横躺"。PNG→JPEG、JPEG→任意格式都会踩中。
- **修复方向**:打开 JPEG/TIFF 后先应用 EXIF 方向(如 `ImageOps.exif_transpose`),或在清元数据前读取并应用 Orientation 后再清除。

### 4. `await f.read()` 在 try 之外,中途失败会泄漏任务目录并丢弃已转换结果

- **位置**:`PictureSwitchService.convert_stream` 循环内,`content = await f.read()` 位于 `try:` 之前;`task_dir` 在此之前已经 `mkdir`。
- **后果**:第 N 个文件的读取一旦抛异常(客户端断开、连接中断等),函数直接退出,`self._task_store.register` 永远不执行 → `task_dir` 不进 LRU/定时清理,磁盘泄漏;前面已成功转换并写盘的文件也全部作废。定时清理机制对该任务完全失效。
- **修复方向**:把 `read()` 纳入异常处理范围;失败时清理 `task_dir` 或仍执行 register 让定时清理兜底。

## 二、逻辑缺陷与边界问题

### 5. 魔数检测"失败回退扩展名",与注释声称的"绕过扩展名伪造"语义不符

- **位置**:`PictureSwitchUtils.detect_format_by_magic` 最后一行 `return _detect_by_extension(filename)`
- **问题**:
  - 一个任意内容的文件只要命名 `.png`,就会绕过魔数失败、按 PNG 去 `Image.open`,靠异常兜底报"文件损坏"——没有真正"绕过伪造",只是把识别失败推迟到解码阶段;
  - 反向场景:JPEG 内容命名 `.png`,魔数识别为 JPEG 并按 JPEG 打开成功,但结果里 `original_format` 取的是**扩展名**(`ext.lstrip(".")` = "png"),报告的原始格式与真实格式不符,前端展示错误。
- **修复方向**:明确策略(魔数失败即拒绝,或以检测结果为准回写 `original_format`),并让 `original_format` 字段以检测到的真实格式为准。

### 6. `get_filename` 负索引越界

- **位置**:`PictureSwitchTaskStore.get_filename`,`stored[index].converted_name if index < len(stored) else "converted"` 只查上界,不查 `index < 0`。
- **后果**:负 index 会命中 Python 列表负索引,返回最后一个文件的名字。目前 `download_single` 先调 `get_file_path`(它有 `index < 0` 检查)间接挡住,但该函数自身不安全,调用顺序一变就会暴露。
- **修复方向**:`get_filename` 内补充 `index < 0` 判断。

### 7. fill 模式输出可能比目标尺寸小(round 误差)

- **位置**:`PictureSwitchUtils._fill_into` 用 `round()` 取整;`PictureSwitchPILService.center_crop_to` 用 `min(w, left + target_w)` 封顶。
- **后果**:如目标 1000×1000、原图 1001×4000,`_fill_into` 得 999×3996,裁切后输出 999×1000,比用户指定的精确尺寸小 1px。fill 语义("精确填满")不严格成立。偏差 ≤1px,轻微。
- **修复方向**:`_fill_into` 改用向上取整(保证至少填满边界)后再裁切。

### 8. 保存前色彩模式兜底不完整

- **位置**:`PictureSwitchService._convert_one_sync` 只有 JPEG(`convert("RGB")`)和 GIF(`convert("P")`)两个保存前兜底。
- **问题**:PBM/PGM/PPM/ICO/TGA 等目标格式没有对应兜底,完全依赖 `resolve_color_mode` 的判断与 Pillow 编码器自身兼容性(如原图 RGB 转 PBM、`"1"` 模式转 TGA 等),不兼容时直接落到"转换失败"的通用错误。
- **修复方向**:为每个输出格式列出允许的模式集,保存前统一检查并转换。

### 9. `target_format / resize_mode / color_mode / svg_mode` 无服务端白名单

- **位置**:`PictureSwitchController.convert_picture` 的 Form 声明,枚举字段没有 `pattern`/`Literal` 约束。
- **后果**:`target_format="xyz"` → `img.save(format="XYZ")` KeyError;`color_mode="abc"` → `img.convert("abc")` ValueError;`svg_mode` 任意非 "embed" 值都会静默走 vectorize 分支。虽然都有兜底不崩,但错误信息暴露内部异常字符串,且属于缺失校验。
- **修复方向**:Controller 层对这四个字段做枚举校验(与 `FORMAT_DETAILS`/常量对齐)。

### 10. SVG `viewBox` 逗号分隔解析失败,4096 限制失效

- **位置**:`PictureSwitchImageIO.open_image` 的 SVG 分支,`parts = vb.split()` 只按空格分割。
- **问题**:SVG 规范允许 `viewBox="0,0,100,100"` 逗号分隔,此时 `parts` 只有 1 个元素 → 走 `width/height` 属性;若 width 又是 `"100%"`,`float()` 抛 ValueError 被吞 → `nat_w/nat_h` 为 0 → 4096 渲染限制失效。
- **后果**:超宽 SVG 不受输出宽度限制,内存风险。
- **修复方向**:viewBox 解析同时兼容逗号与空白分隔(先 `replace(",", " ")` 再 split);解析失败时给出明确错误而非静默。

## 三、性能隐患

### 11. SVG vectorize 算法复杂度失控

- **位置**:`PictureSwitchSvgService.save_as_svg` 与 `trace_contours`
- **现状**:量化层级最高 16 → 最多 16³=4096 种颜色,每种颜色执行一次 `np.all(q_arr == ref_color, axis=2)` 全图比较;`trace_contours` 再对每个连通区域做 BFS 和极角排序。
- **后果**:高分辨率/颜色丰富的照片转 SVG(vectorize)耗时不可接受;且 `_PIL_EXECUTOR` 只有 2 个 worker,一次这样的任务会长时间占满线程池,阻塞其他所有用户的转换请求。位图输入没有像素上限保护(只有 SVG 输入有 4096 限制)。
- **修复方向**:限制 vectorize 的输入像素总量/层级上限;或改用 `skimage.measure.find_contours` 等更优算法;必要时对超大图直接拒绝并给出明确提示。

### 12. 批量转换完全串行,线程池未利用

- **位置**:`PictureSwitchService.convert_stream`
- **现状**:逐文件 `await loop.run_in_executor` 串行提交,50 个文件线性累积;`max_workers=2` 形同虚设(只有并发请求之间才共享)。
- **修复方向**:分批并发提交(如 `asyncio.gather` 按批次提交到线程池),控制同时处理的文件数。

### 13. zip 打包与 LRU 删除在事件循环里同步执行

- **位置**:`PictureSwitchTaskStore.register`
- **现状**:`zipfile` 写入和 `shutil.rmtree` 都是同步阻塞 IO,大文件批量任务会卡住整个事件循环(影响同进程的其他 HTTP/Socket.IO 请求)。
- **修复方向**:将 zip 打包与目录删除移到线程池或后台任务执行。

### 14. WebP 固定 `method=6`

- **位置**:`PictureSwitchUtils.get_save_kwargs`
- **现状**:WebP 固定 `method=6`(最慢/压缩率最高),大图单文件编码可能数十秒,叠加第 12 条的串行,批量体验差。
- **修复方向**:按图片尺寸动态选择 method,或提供可配置项。

## 四、低置信 / 依赖依赖库行为(需实测确认)

### 15. P 模式透明图直接 `bg.paste(img)` 不带 mask

- **位置**:`PictureSwitchSvgService.save_as_svg` 中 P 模式分支 `bg.paste(img)`。
- **问题**:透明索引是否被正确填充为背景色,取决于 Pillow C 层对 P 模式 `transparency` info 的处理;若未生效,透明像素会以调色板索引色实体出现。
- **建议**:统一转为 RGBA 后用 alpha 通道做遮罩合成,消除对库行为的依赖。

### 16. 多帧输入只对 GIF 有处理

- **位置**:`_convert_one_sync` 仅对 `detected == "GIF"` 且 `is_animated` 做首帧处理。
- **问题**:APNG(检测为 PNG)、多帧 AVIF(`get_image(0)` 取首帧)均无提示、无处理,与 GIF 的"仅保留首帧 + warning"策略不一致。
- **建议**:统一多帧输入的策略并给用户可见提示(而非仅日志)。

### 17. CMYK 等特殊模式转 PNG/TGA 等格式

- **问题**:auto 模式下保留原模式,编码器不支持时落入通用错误,没有统一降级。
- **建议**:实测 Pillow 当前版本对各模式组合的写入行为,补齐模式兼容矩阵。
