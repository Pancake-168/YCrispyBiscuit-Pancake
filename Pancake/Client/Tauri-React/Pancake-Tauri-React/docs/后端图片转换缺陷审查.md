# 后端图片转换缺陷审查

> 审查日期：2026-07-10
>
> 审查方法：以前端 API 协议为基准，逐字段交叉对比后端源码。
> 前端参考：[图片转换API分析文档](图片转换API分析文档.md)
>
> 审查范围：
> - `app/controllers/PictureController.py` — API 端点
> - `app/schemas/PictureSchema.py` — Pydantic 模型
> - `app/services/PictureService.py` — 转换核心服务
> - `app/utils/PictureUtils.py` — 工具函数/格式数据

## 一、严重缺陷

### 1. Pydantic FormatDetail 缺少 `supports_lossless` 字段 → WebP 无损开关永不显示

**文件：** `app/schemas/PictureSchema.py:12-20`

`FormatDetail` Pydantic 模型只定义了 5 个字段：

```python
class FormatDetail(BaseModel):
    extensions: List[str]
    mime_type: str
    supports_transparency: bool
    supports_animation: bool
    lossy_options: bool
    quality_range: Optional[List[int]] = None
```

而 `app/utils/PictureUtils.py:115-124` 中 `FormatDetail.to_dict()` 返回 7 个字段，包含 `supports_lossless`。但 Pydantic v2 默认 `extra='ignore'`，构造 `FormatDetail(**val)` 时 `supports_lossless` 被**静默丢弃**。

**后果：** API 返回的 JSON 中 WebP 的 `format_details` 不含 `supports_lossless: true`。前端判断 `targetDetail?.supports_lossless === true`（PictureSwitchPage/index.tsx:85）永远为 `false`，WebP 无损压缩开关**从不出现**。

**修复方向：** 在 `PictureSchema.py` 的 `FormatDetail` 中补上：
```python
supports_lossless: bool = False
```

### 2. `output_formats` 包含重复扩展名 → 前端下拉框重复项 + `format_details` 查找失败

**文件：** `app/utils/PictureUtils.py:37-39, 59-61`

```python
OUTPUT_FORMATS: Dict[str, str] = {
    k: v for k, v in EXT_TO_FORMAT.items() if v not in ("HEIF", "SVG")
}
OUTPUT_EXTENSIONS = sorted(OUTPUT_FORMATS.keys())
```

`EXT_TO_FORMAT` 中 `.jpg` 和 `.jpeg` 都映射到 `JPEG`，`.tif` 和 `.tiff` 都映射到 `TIFF`。`OUTPUT_EXTENSIONS` 是扩展名字典的键去重，只按后缀字符串做 key，两个 `JPEG` 和 `TIFF` 的后缀都保留了，导致：

```
output_formats = ["avif", "bmp", "gif", "ico", "jpeg", "jpg", "pbm", "pgm", "png", "ppm", "tga", "tif", "tiff", "webp"]
```

**后果 A：** 前端下拉框出现 `JPEG` 和 `JPG` 两个选项、`TIFF` 和 `TIF` 两个选项（PictureSwitchPage/index.tsx:134 按 `f.toUpperCase()` 渲染）。

**后果 B：** `format_details` 的 key 只有 `"jpeg"` 和 `"tiff"`。用户若选中 `"jpg"` 或 `"tif"`，`format_details["jpg"]` 为 `undefined`，导致 `targetDetail` 为 `undefined`：
- `showQuality` → `undefined?.lossy_options === true` → `false`，质量滑块不显示
- `showLosslessSwitch` → `undefined?.supports_lossless === true` → `false`
- 背景填充色 → `undefined && !undefined.supports_transparency` → falsy，不显示

**后果 C（严重——直接崩溃）：** 发送 `target_format="jpg"` 到后端时：

1. `get_pillow_format("jpg")` 在 `EXT_TO_FORMAT` 中查不到（key 需要带点 `.jpg`），返回 `None`
2. `target_pillow_fmt = "JPG"`（fallback: `params.target_format.upper()`）
3. `resolve_color_mode(img_mode, "JPG", "auto", ...)` 中 `"JPG"` 不在 `no_alpha_formats` 集合内，如果源图含透明通道则不会强制 RGBA→RGB，返回 `"RGBA"`
4. `save_format` = `"JPG"`，`save_format == "JPEG"` 为 `False`，跳过 JPEG 的色彩模式兼容处理
5. `get_save_kwargs` 中 `fmt = "JPG"`（同样是 `get_pillow_format` 返回 `None` 后的 `.upper()` fallback），`fmt == "JPEG"` 不匹配，**所有保存参数（quality、optimize）全部丢弃**
6. `img.save(buf, format="JPG")` → Pillow 不识别 `"JPG"`，**抛出 `ValueError: unknown file format: JPG`**

同理选 `"tif"` 时 `format="TIF"` 也会 crash（Pillow 规范名是 `"TIFF"`）。两者均**直接崩溃**，不是 quality 丢失的问题。

**修复方向：** `output_formats` 应对格式名去重而非对扩展名去重：
```python
# 按 FORMAT_TO_EXT 的 key（格式名，非扩展名）生成输出列表
# 如 {"png", "jpeg", "webp", ...}，不带点的小写格式标识
```
需确保与 `format_details` 的 key 对齐。

### 2.1 根因：`get_pillow_format` 在整个 convert 路径中结构性失效

**文件：** `app/utils/PictureUtils.py:330-332`

```python
def get_pillow_format(ext: str) -> Optional[str]:
    return EXT_TO_FORMAT.get(ext.lower())
```

`EXT_TO_FORMAT` 的所有 key 都带前导点（`.png`、`.jpg`、`.jpeg`...），但 `target_format` 来自前端 `output_formats`，不含点（`"png"`、`"jpeg"`...）。此函数在 convert 路径的所有调用处（`_convert_one_sync:307`、`get_save_kwargs:366`）**永远返回 `None`**，100% 依赖 fallback `params.target_format.upper()`。

这意味着：
- 只要 `.upper()` 的结果与 Pillow 规范名完全一致（如 `"PNG"`、`"WEBP"`、`"JPEG"`），侥幸能工作
- 只要出现偏差（`"JPG"` ≠ `"JPEG"`、`"TIF"` ≠ `"TIFF"`），直接崩溃
- Defect 2 的 `jpg`/`tif` 崩溃只是症状，根因是这条断裂的格式名解析链

**调用链分析：**

| 调用位置 | 传入值 | 行为 |
|---------|--------|------|
| `_convert_one_sync:307` | `params.target_format`（无点） | 永远返回 `None`，靠 `.upper()` fallback → `"JPG"`、`"TIF"` 等非规范名 |
| `get_save_kwargs:366` | `target_format`（无点） | 同上，保存参数全部丢失 |

**修复方向：** `get_pillow_format` 需同时兼容带点和不带点的输入：
```python
def get_pillow_format(ext: str) -> Optional[str]:
    ext_lower = ext.lower()
    if ext_lower in EXT_TO_FORMAT:
        return EXT_TO_FORMAT[ext_lower]
    return EXT_TO_FORMAT.get(f".{ext_lower}")
```
配合 `output_formats` 去重（按格式名而非扩展名），可彻底消除此链上的所有问题。

### 3. AVIF 编码完全忽略 quality 参数

**文件：** `app/services/PictureService.py:357-358, 482-504`

`_convert_one_sync` 中 AVIF 分支：

```python
if target_pillow_fmt == "AVIF":
    converted_data = self._encode_avif(img)  # 未传 quality
```

`_encode_avif` 方法签名和实现（PictureService.py:482-504）：

```python
def _encode_avif(self, img: Image.Image) -> bytes:
    # ...
    encoder = pyavif.Encoder(tmp_path, img.width, img.height, channels, 8)
    encoder.add_frame(arr)
    encoder.finish()
```

全程无 quality 参数。而 `get_save_kwargs` 中 AVIF 的 quality 处理（PictureUtils.py:382-384）是**死代码**——因为 AVIF 走 `_encode_avif` 分支，从不调用 `get_save_kwargs`。

**后果：** 前端 AVIF 质量滑块形同虚设，无论拖到 0 还是 100，输出文件质量始终由 pyavif 默认值决定。

**修复方向：** `_encode_avif` 应接收 quality 参数并传递给 pyavif.Encoder；或 AVIF 统一走 Pillow save 路径（若 Pillow 12+ 已内置 AVIF 读写则无需 pyavif）。

## 二、中等问题

### 4. `get_formats` 返回 `heif` 详情但 heif 不可输出

**文件：** `app/services/PictureService.py:100-109`

`get_supported_formats` 返回全部 `FORMAT_DETAILS`（含 `heif`），但 `output_formats` 不含 `heif`（PictureUtils.py:37-39 排除了 HEIF）。

**后果：** 前端收到 `format_details.heif` 但 `output_formats` 无 `"heif"`，该详情永远不会被 UI 使用。不产生 bug，但数据冗余且容易误导。

**修复方向：** `get_supported_formats` 可只返回 `output_formats` 中包含的格式的详情；或保留全量但无影响。

---

### 5. `convert` 方法是同步死代码

**文件：** `app/services/PictureService.py:115-176`

`convert(self, file_datas: List[Tuple[str, bytes]], params)` 方法在所有 for 循环中同步调用 `self._convert_one_sync()`，未使用 `run_in_executor`。Controller 实际调用的是 `convert_stream`（PictureController.py:103），`convert` 未被任何端点使用。

**后果：** 当前不影响运行（Controller 不用它）。但若未来有人误用此方法，会在 asyncio 事件循环中执行同步阻塞，阻塞所有并发请求。

**修复方向：** 删除或标注 `@deprecated`，或改为与 `convert_stream` 一致的线程池执行。

---

### 6. `background_color` 无格式校验

**文件：** `app/controllers/PictureController.py:74`

```python
background_color: str = Form("#FFFFFF", description="透明转不透明填充色"),
```

无正则或长度校验。传 `"red"`、`"#GGG"` 等非法值会在 PIL `Image.new("RGB", ..., background_color)` 时抛异常，错误信息不友好。

**后果：** 用户通过非前端途径（curl/API 直接调用）传无效颜色值时 crash。

**修复方向：** 添加 `pattern="^#[0-9a-fA-F]{6}$"` 校验或服务端 try/except 兜底。

## 三、轻微问题 / 观察项

### 7. JPEG quality 的 Form 约束 `ge=0` 与实际不匹配

**文件：** `app/controllers/PictureController.py:62`

```python
quality: Optional[int] = Form(None, ge=0, le=100, ...),
```

JPEG 不接受 `quality=0`（Pillow 限制 1–100）。`get_save_kwargs`（PictureUtils.py:374）已做 `max(1, min(100, quality))` 钳位，但 Form 级别的 `ge=0` 与 JPEG 实际下限矛盾，可能让调用方误以为 `quality=0` 是合法值。

**修复方向：** 将 `ge=0` 改为 `ge=1`。WebP/AVIF 支持 0 的参数由 `get_save_kwargs` 各自处理。

---

### 8. BMP `supports_transparency` 标记为 `false` 可能不准确

**文件：** `app/utils/PictureUtils.py:131`

```python
"bmp": FormatDetail([".bmp"], "image/bmp", False, False, False, None),
```

32 位 BMP（BITMAPV4HEADER/V5HEADER）理论上支持 alpha 通道，Pillow 也可读写 32-bit RGBA BMP。标记为 `false` 可能是保守选择（许多老旧工具不支持 BMP alpha），但在 Pillow 12.x 环境下是支持的。

**修复方向：** 如 Pillow 版本 ≥ 10.0，可考虑改为 `True`。但属于可选优化，当前标记为 `False` 是安全行为（不会产生透明通道丢失的意外）。

---

### 9. `resolve_color_mode` 的 `no_alpha_formats` 不覆盖非规范格式名

**文件：** `app/utils/PictureUtils.py:295`

```python
no_alpha_formats = {"JPEG", "BMP", "GIF", "PPM", "PBM"}
```

集合全是 Pillow 规范大写名。当 `get_pillow_format` 返回 `None`、fallback 产生非规范名时（如 `"JPG"`、`"TIF"`），格式名不在集合内，RGBA→RGB 强制转换被跳过。结合 Defect 2 选 `"jpg"` + RGBA 源图的场景：

```
target_pillow_fmt = "JPG" → not in no_alpha_formats
→ resolve_color_mode 返回 "RGBA"
→ 后续 save_format == "JPEG" 为 False → 跳过 convert("RGB")
→ img.save(buf, format="JPG") with RGBA mode
→ OSError: cannot write mode RGBA as JPEG
```

这是 Defect 2 的第二条崩溃路径。修复 `get_pillow_format`（见 Defect 2.1）后此问题自然消除——因为格式名会被规范化为 `"JPEG"`。

### 10. `OUTPUT_EXTENSIONS` 命名误导且语义混用

**文件：** `app/utils/PictureUtils.py:59-61`

```python
OUTPUT_EXTENSIONS = sorted(OUTPUT_FORMATS.keys())
# 值：['.avif', '.bmp', '.gif', '.ico', '.jpeg', '.jpg', ...]
```

变量名暗示是"输出扩展名"（带点），但在 `get_supported_formats:107` 中被去点后当"格式标识"用：

```python
"output_formats": [ext.lstrip(".") for ext in OUTPUT_EXTENSIONS]
```

这是 Defect 2 重复问题的语义根因——去重应按**格式名**（`FORMAT_TO_EXT` 的 key，如 `"JPEG"`）而非**扩展名字符串**（`.jpg` 和 `.jpeg` 是两个不同字符串，尽管对应同一格式）。

**修复方向：** 新增按格式名去重的常量：
```python
OUTPUT_FORMAT_NAMES = sorted(set(v.lower() for v in OUTPUT_FORMATS.values()))
# → ["avif", "bmp", "gif", "ico", "jpeg", "pbm", "pgm", "png", "ppm", "tga", "tiff", "webp"]
```
直接用于 `output_formats` 字段，与 `format_details` 的 key 天然对齐。

### 11. SVG 渲染无尺寸限制

**文件：** `app/services/PictureService.py:438-441`

```python
if detected_format == "SVG":
    import cairosvg
    png_data = cairosvg.svg2png(bytestring=data)
    return Image.open(io.BytesIO(png_data))
```

`cairosvg.svg2png` 未传 `output_width` / `output_height`。超大 SVG（如 `width="10000" height="10000"`）会按原始尺寸渲染到内存位图，可能导致内存暴涨。

**修复方向：** 限制渲染尺寸上限，如 `output_width=4096, output_height=4096`。

### 12. `zip_url` 后端生成但前端完全不使用

**文件：** `app/services/PictureService.py:229-235`、`app/schemas/PictureSchema.py:54`

后端在 `convert_stream` 中构造 `zip_url = f"/api/picture/download/batch/{task_id}"` 并存入 `ConvertResponse.zip_url`，但前端（PictureSwitchPage/index.tsx:300-303）下载时直接调用 `getBatchDownloadUrl(taskId)` 拼接路径，完全忽略响应中的 `zip_url` 字段。

**修复方向：** 删除后端 `zip_url` 生成逻辑和 Schema 字段，或让前端改用响应中的字段（后者改前端即可）。

### 关于 `_fill_into` 缩小行为（审查者遗漏 5）：**非 bug**

审查者提出 `_fill_into` 在源图大于目标尺寸时会缩小再裁切。经核实，这正是 `fill` 模式（类比 CSS `object-fit: cover`）的正确行为——图片大于容器时应当缩小至短边填满再居中裁切，而非放大溢出。

```
例：3000×2000 源图 → 500×500 目标
ratio = max(500/3000, 500/2000) = 0.25
→ 缩至 750×500 → 居中裁切至 500×500  ✓ 正确
```
